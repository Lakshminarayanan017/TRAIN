# assets.csv — Asset master (Data Spec §8.3)

The fifth reference table in the build order (§12.5), and the first that is **synthesised**
rather than authored. It is also the escalation-risk model's entire feature source: §12.2 lists
that model as reading `11.2` expanded to defect-days **plus this table**, and §8.3 flags
`cumulative_tonnage_gmt` as *"a strong escalation predictor"*.

Generated by `data/generator/build_assets.py` with a fixed seed (26027, the problem statement
number). Regenerating produces a byte-identical file.

## Schema (Data Spec §8.3)

| Column | Type | Req | Notes |
|---|---|---|---|
| `asset_id` | string | yes | `PT-TRL-04`. Primary key. `<type prefix>-<scope>-<nn>`. |
| `asset_type` | enum | yes | One of the 16 values in §12.1. |
| `department` | enum | yes | `ENG` / `TRD` / `SNT` — who maintains it. |
| `block_section_id` | ref | no | Null for node-located assets. |
| `station_code` | ref | no | Null for edge-located assets. |
| `km` | float | yes | Chainage on the section's home corridor. |
| `criticality_class` | enum | yes | `A` / `B` / `C`. |
| `install_date` / `last_overhaul_date` | date | no | Age features. |
| `cumulative_tonnage_gmt` | float | no | Tonnage-bearing assets only. |
| `failure_count_12m` | int | no | Failures in the trailing year. |

Exactly one of `block_section_id` / `station_code` is populated on every row; the validator
fails the build otherwise, since an asset on neither has no place in the graph and no task can
be raised against it.

## An asset here is a maintenance unit, not a physical item

A `rail` row is the rail panel group a defect is booked against, not one rail. A `mast` row
stands for a run of structures, not a single mast at 60 m spacing — modelling that literally
would give a hundred thousand rows on this network. The spec's §12.4 volume of **2,000–5,000**
is the tell: that number only makes sense at the granularity work is actually booked at.

**2,413 rows.** 2,101 edge-located, 312 node-located.

| Department | Rows | |
|---|---|---|
| ENG | ~940 | rail, sleeper, ballast, turnout, bridge, level crossing |
| TRD | ~740 | OHE span, contact wire, mast, insulator, substation |
| SNT | ~730 | signal, point machine, track circuit, axle counter, interlocking |

Densities are **per line-km**, so a quadruple section carries four times the plain-line assets
of a single-line one. That is the behaviour maintenance load should have, and it is what makes
the busy suburban corridor generate proportionally more work than the branch without any
special-casing in the task generator.

## The correlations are deliberate, and they are the point

The escalation model is supposed to learn that heavily worked, old, high-criticality assets
fail more. If the features were drawn independently there would be nothing to learn, and a
model fitted on them would still produce plausible-looking output — which is worse than useless,
because it looks like it worked.

So the generator builds the relationship in explicitly:

- `cumulative_tonnage_gmt` = section train count × tonnes per train by `traffic_type` × age.
  Freight rakes are modelled at 3,400 t against an EMU's 420 t, so the northern line ages track
  far faster than its modest train count alone would suggest — which is true, and is why port
  traffic drives P.Way renewal on that road.
- `failure_count_12m` is a Poisson draw whose rate rises with age, tonnage and criticality.
- `last_overhaul_date` is pulled forward for heavily worked assets — they reach overhaul at 35%
  of nominal life rather than 55%.

Measured on the emitted file:

| Slice | Mean `failure_count_12m` |
|---|---|
| Lowest tonnage quartile | 0.35 |
| Highest tonnage quartile | 1.43 |
| Criticality A / B / C | 0.86 / 0.66 / 0.51 |

A 4× spread across the tonnage range, and a monotone gradient across criticality. That is real
signal, and it is the honest way to demonstrate the model — the relationship was put there on
purpose and the README says so, rather than being presented as a discovery.

**This is also the limit of what the model can claim.** A model trained on this data recovers
the generator's own assumptions. It validates the pipeline, not the railway. Any accuracy figure
quoted from it measures whether the code works, never whether the physics is right.

## Siting rules

- **Edge assets** are placed uniformly along the section between 2% and 98% of its length, on
  each line separately. The validator confirms every `km` lies inside the section it claims.
- **Structures** — bridges and level crossings — are counted once per *span*, not per line,
  since a bridge carries all four tracks. They are attached to the span's first line.
- **Node assets** sit at stations with `has_yard = true`, scaled by `route_capacity`: turnouts
  and point machines at 1.5 per route, one interlocking each, plus yard ballast and yard OHE.
- **Yard ballast and yard OHE exist because node tasks need them.** `ENG-YARD-PWAY` acts on
  `ballast` and `TRD-OHE-YARD` on `OHE_span`, both node-located. Without those assets sited at
  stations the tasks could never be raised. The validator now enforces this in both directions:
  every asset type must have a task type acting on it, and every node task's asset type must be
  sited at some station.
- **OHE is sited only where the station touches an electrified section.** Kanchipuram sits at
  the boundary — `WJ-CJ` is electrified, `CJ-TMLP` is not — so it does carry OHE; Thakkolam and
  Tirumalpur have no yard and so no node assets at all.
- **Substations** are sparse, at seven of the larger yards, roughly one per 25 electrified
  route-km.

## Dating

All ages are computed against a fixed `TODAY = 2026-09-07`, a few days after the `raised_date`
values in the §9.1 sample records. Using the real clock would make ages, tonnages and failure
counts drift between a rehearsal and the presentation, which §12.5 warns about explicitly.
Service lives run from 12 years (ballast) to 80 (bridge), and install dates spread uniformly
over that life, so the corpus contains both nearly-new and nearly-life-expired assets.

## Data provenance (spec §12.3)

§12.3 classes the asset base under **synthesise**. Nothing in this file is a real Chennai
Division asset register, and no claim is made that it is. What is grounded is the *structure*:
the asset type enumeration is the spec's own §12.1 list, departmental ownership follows standard
IR practice, siting follows the real section geometry in `block_sections.csv`, and relative
tonnage between freight, trunk, mixed and suburban traffic reflects real rake weights.

**Approximate / to verify before a submitted build (spec §7.1 caveat).** Asset densities per
line-km, service lives, tonnage per train, criticality thresholds and the failure rate model are
all reasoned engineering approximations. On deployment this table is replaced wholesale by the
division's TMS / SMMS / TDMS asset registers, which is where the real `cumulative_tonnage_gmt`
and failure history live. The relative comparison between scheduling strategies is the claim;
the absolute asset condition is not.
