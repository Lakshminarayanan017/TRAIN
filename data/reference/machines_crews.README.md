# machines.csv and crews.csv — Machine and crew master (Data Spec §8.6)

The last two reference tables in the build order (§12.5), and the ones that turn Blueprint
§7.6's *"two hard constraints that prevent impossible plans"* from prose into arithmetic:

> **Machine transit feasibility.** If a tamper is physically four hours away and the block
> starts in two, that is impossibility, not risk.
>
> **Crew rest and duty hours.** Without this the optimiser will assign the same crew a Tuesday
> night block and a Wednesday morning block. Duty rules are non-negotiable; a plan that
> breaches them is infeasible, not merely undesirable.

Both are read by the weekly optimiser, the duration predictor and the availment risk model
(§12.2). Generated by `data/generator/build_resources.py`, fixed seed 26027.

# machines.csv

## Schema (§8.6)

| Column | Type | Req | Notes |
|---|---|---|---|
| `machine_id` | string | yes | `TAMP-SR-07`. Not unique on its own — see below. |
| `machine_type` | enum | yes | The six classes of the `machine_required` enum, less `none`. |
| `home_base` | ref | yes | Station the machine is allotted to. |
| `current_section` | ref | yes | Block section it currently stands on. |
| `available_from` / `available_to` | datetime | yes | One availability window. |
| `output_rate` | float | no | Metres per hour; feeds duration estimation. |
| `transit_time_h` | float | yes | Hours to reposition per adjacent section. |

## One row per machine per window, not per machine

§8.6 calls `available_from` / `available_to` an **availability calendar**, and §12.4 sizes this
table at ~50 rows — against a division fleet that is realistically under twenty. Both facts fit
only if the row is `(machine, window)` rather than `(machine)`.

**49 rows over 17 machines**, two to four windows each. The primary key is
`(machine_id, available_from)`; the validator enforces uniqueness on that pair and fails if a
machine ever changes class between its own windows.

The **gaps between a machine's windows** are its own shop maintenance and commitments elsewhere.
They are not padding — they are what makes the transit constraint bite. A tamper that is
available all month is not a constraint at all.

| `BCM` | 1 | 60 | 2.5 | AJJ |
| `rail_grinder` | 1 | 500 | 1.5 | AJJ |

**`TAMP-SR-07` is the §8.6 example row, based at AVD exactly as the spec has it.** Fleet
numbering is deliberately non-contiguous (03, 05, 07) the way a real zonal fleet's is, so the
anchor sits naturally rather than looking retrofitted.

Output rates are ordered the way the work actually is: a BCM deep-screening at 60 m/h is two
orders of magnitude slower than a USFD car running at line speed. Transit times scale inversely
— the slowest machines are also the slowest to move, which is precisely why the one BCM serving
the whole pilot cannot be in two corridors on the same night.

## Scarcity is the design, and it is in the right place

Headcount is not the binding constraint — **qualification is**. Against 26 general gangs there
are only 10 renewal crews, 8 test crews and 4 substation crews. Rail renewal, USFD testing and
substation work are therefore contended in a way that routine welding is not, which is how a
real division actually runs and what gives the optimiser's qualification-matching constraint
something to fail on.

Twelve crews are `day_only` — the substation and telecom crews, whose work is indoor and does
not touch the track. Everything that does touch the track rotates, because that is when blocks
happen. `max_consecutive_nights` is 3 for `rotating_3`, 2 for `rotating_2` and **0 for
`day_only`**; the validator fails the build on a `day_only` crew carrying a night allowance, or
a rotating crew that can never work a night.

`min_rest_hours` is 12 throughout; `max_weekly_duty_hours` is 48–54.

## A bug worth recording

The first generated establishment rotated archetypes by base index, and the rotation never
advanced far enough to create the renewal, inspection, substation and telecom crews. **Ten task
types were left with nobody qualified to do them** — silently, since every crew row was
individually valid.

Fixed by setting explicit per-archetype counts. The validator now fails the build if any task
type has zero qualified crews, so this cannot recur unnoticed. It is the same class of defect as
the unsited yard assets caught while building `assets.csv`: the individual rows were fine and
the *relationship between tables* was broken. Cross-table checks are where the value is.

## Data provenance (spec §12.3)

§12.3 classes crew and machine calendars under **synthesise**. Nothing here is a real Southern
Railway roster or fleet register.

What is grounded: the machine classes are the spec's own §12.1 enumeration; departmental
structure and the gang / machine-crew / works-crew split follow standard IR field organisation;
bases are real stations with yards; and the duty limits are of the right order for IR working
hours rules.

**Approximate / to verify before a submitted build (spec §7.1 caveat).** Fleet size and
composition, crew establishment and sizes, output rates, transit times and the exact duty limits
are reasoned engineering approximations. `min_rest_hours`, `max_consecutive_nights` and
`max_weekly_duty_hours` in particular must be replaced with the division's actual duty rules
before any operational use — they are enforced as **hard constraints**, so a wrong value produces
a plan that is confidently infeasible rather than obviously wrong.
