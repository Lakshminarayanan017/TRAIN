# defect_lifecycle.csv — Defect lifecycle (Data Spec §11.2)

The escalation-risk training set. One row per defect; at training time each is
expanded into one row per day it stayed open, for discrete-time survival modelling
(Blueprint §8.2). `escalated` is the label.

Generated by `data/generator/build_defect_lifecycle.py`; checked by
`data/checks/validate_history.py`. **3,500 defects** over ~18 months (219 still
open — the censored cases the survival model needs), **587 escalated**.

## Schema (Data Spec §11.2)

`defect_id`, `asset_id`, `defect_type`, `severity_at_raise`, `raised_date`,
`attended_date`, `days_open`, `temporary_repair_applied`, `escalated`,
`escalation_type`, `escalation_date`. `attended_date` is recorded but is **never a
model feature — it is leakage** (§11.2).

## The confounding trap is built in on purpose (Blueprint §8.2)

This is the entire difficulty of the model, and the data reproduces it. The *true*
daily hazard genuinely rises with severity and with asset condition (tonnage, age,
failures). But **severe defects are attended fastest**, so they spend few days
open and rarely reach escalation — while minor defects sit for weeks and escalate
more often. In the raw data the relationship looks **inverted**:

| severity | avg days_open | raw escalation |
|---|---|---|
| IMDT | 1 | **5%** |
| 1 | 4 | 6% |
| critical | 4 | 10% |
| major | 14 | 15% |
| minor | 38 | **18%** |
| 2 / 3 (rail) | 14 / 42 | 20% / 22% |

A model that asks *"does this severity escalate?"* learns that IMDT is the safest
class — exactly backwards. Only a model that asks *"given it is still open on day
k, what is today's hazard?"* recovers the truth, because the daily hazard **is**
higher for IMDT. `temporary_repair_applied` lowers the hazard (×0.4).

## Grounded

Defects are raised against the **real assets** in `assets.csv`, weighted by the
failure history, criticality and tonnage those assets carry — so defects cluster
on the track that genuinely wears fastest, and the escalation model's condition
features move the target for a real reason. `defect_type` is drawn from a
per-asset-type vocabulary; the escalation the ML sees is otherwise synthesised,
because no service records defect-day escalation labels.
