# emergency_events.csv — Emergency event log (Data Spec §11.4)

The disruption record. An emergency is not an input to the planner, it is an input
to reality (Blueprint §10.1): by the time it is logged the section is seized and
the crew diverted. This log is the shape the emergency re-planner learns — how
often events happen, how long a section is held, and which resources they pull off
planned work.

Generated by `data/generator/build_emergency_events.py`; checked by
`data/checks/validate_history.py`. **180 events.**

## Schema (Data Spec §11.4)

`event_id`, `event_type`, `block_section_id`, `km`, `occurred_at`, `duration_min`,
`resources_consumed` (`;`-list of crew/machine refs), `blocks_invalidated`
(`;`-list of block refs), `followup_task_id`.

## Grounded seasonality (spec §12.3 names the monsoon and heat as real)

Event timing follows Chennai's real calendar, and event location follows the asset
type and traffic each failure mode belongs to:

- **`rail_fracture`** clusters in the **April–June** pre-monsoon heat (the rail
  buckles) and lands on the heavy-tonnage trunk and freight lines.
- **`OHE_failure`** and **`weather`** cluster in the **Oct–Dec north-east
  monsoon**; OHE events only on electrified sections.
- **`cattle_run_over`** favours the outer / branch stretches and the dawn hours;
  **`point_failure`** / **`signal_failure`** fall through the year on the busier
  running lines.

Event durations match the type (a weather washout holds a section far longer than
a cattle strike). Every reference resolves: `resources_consumed` names real crews
and machines of the attending department, `blocks_invalidated` names real
`block_executions`, and `followup_task_id` points at a real
`origin = emergency_followup` task **of the same department** — the permanent
repair the failure spawns (Blueprint §10.6). Frequencies and durations are
synthesised at a plausible level, because no queryable log of these exists.
