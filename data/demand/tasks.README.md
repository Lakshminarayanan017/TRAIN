# tasks.csv — The unified task schema (Data Spec §9)

> *"The central artefact of the project. All five points of view, all four models and the
> optimiser read from this one object. Three source systems with three vocabularies collapse
> into it. Build it first and change it reluctantly."* — Data Spec §9

Bucket 2, and the whole demand side. Generated by `data/generator/build_tasks.py`, fixed seed
26027. Validated by `data/checks/validate_demand.py`.

**4,000 rows over a one-year horizon ending 2026-09-07**, of which **283 are pending** — both
on the §12.4 targets (~4,000 tasks, ~300 pending in any week).

## Schema (Data Spec §9)

26 columns: identity (`task_id`, `source_system`, `source_ref`, `department`, `task_type_id`,
`asset_id`), location (`location_kind`, `block_section_id`, `station_code`, `start_km`,
`end_km`, `line_id`), origin and urgency (`origin`, `raised_date`, `days_pending`, `severity`,
`deadline`, `safety_critical`), access and effort (`access_required`, `requested_duration_min`,
`crew_required`, `machine_required`, `materials_ready`), and constraints (`season_restricted`,
`night_permitted`, `status`).

## The derived fields are absent, deliberately

§9 marks eight fields ★ *"Derived by the system — never ingested"*: `geo_key`,
`predicted_duration_p50` / `p80` / `p95`, `escalation_hazard_daily`, `availment_risk`,
`risk_score`, `score_factors`.

**None of them is in this CSV**, and `validate_demand.py` fails the build if any appears. This
is not tidiness. Emitting a `predicted_duration_p80` alongside the data the duration model
trains on would be feeding model output back in as input, and every accuracy figure computed
afterwards would be circular. The eight columns appear only downstream, on objects the system
has computed.

## Composition

| | |
|---|---|
| Department | ENG 2,001 · SNT 1,087 · TRD 912 |
| Origin | overdue 1,252 · defect 1,200 · routine 998 · proactive 337 · emergency_followup 213 |
| Access | traffic_block 1,844 · power_block 909 · disconnection 884 · none 363 |
| Status | done 2,957 · pending 283 · deferred 229 · scheduled 231 · in_progress 168 · cancelled 132 |
| Safety-critical | 459 of 4,000 |

Origin is kept consistent with the catalogue: a task type with a `default_periodicity_days`
cannot raise a `defect`, and a defect-driven type cannot raise `routine` work. The
overdue-versus-routine split is the difference between periodic work done on time and periodic
work that has slipped — which is exactly the population the escalation model exists to rank.

## Arrival is traffic-weighted, and that is what makes merging possible

Spreading 283 pending tasks evenly over 23 spans and 14 yards would put about three on each —
below the *"five to twenty pending tasks"* Blueprint §6.2 assumes, and merges would be rare.

Instead each task draws its asset with weight from `failure_count_12m`, `criticality_class` and
`cumulative_tonnage_gmt`. Those already encode the section's train count and tonnage (see
`assets.README.md`), so the clustering of work onto busy track falls out without any geography
being restated here. The result:

| | |
|---|---|
| Pending pool | **283 tasks over 69 locations** |
| Per location | max 10, median 3 |
| Locations with **2+ departments** pending | **53** |
| Locations with **all three** departments | **17** |

Those 53 are the merge candidates the optimiser is supposed to discover. Without the weighting
they would not exist in useful numbers, and the demonstration would show an optimiser correctly
finding nothing to do.

## Status drives the date, not the other way round

The first generated corpus drew `raised_date` uniformly over the year and then corrected
`status` afterwards — old work could not still be pending, new work could not already be done.
That emptied the pending pool to 121 tasks, because most rows landed months back and were
reclassified as `done`.

Now `status` is drawn first and the date follows from it: open work is recent with a tail of
items that have been waiting, deferred work is at least a month old, closed work is spread over
the year. Same distributions, but the pending pool holds its size. Worth recording because the
failure was silent — every individual row was valid, and only the *aggregate shape* was wrong.

## The §9.1 sample records are present verbatim

The spec calls these three *"the merge candidate the optimiser must discover"* and says to use
them as the first integration test. They are emitted exactly as written, and generated task ids
skip their serials so they stay unique:

| Task | Type | Where | Access | Duration |
|---|---|---|---|---|
| `ENG-2026-04412` | `ENG-RAIL-WELD` | `TRL-AJJ-UP` km 42.10 | traffic_block | 180 min |
| `TRD-2026-01188` | `TRD-OHE-INSP` | `TRL-AJJ-UP` km 40.00–44.00 | power_block | 90 min |
| `SNT-2026-00734` | `SNT-POINT-SERVICE` | node `TRL` | disconnection | 60 min |

All three resolve against real assets — `RL-TRLAJJ-0421`, `OHE-TRLAJJ-0402` and `PT-TRL-04` are
in `assets.csv`, the first two injected as anchors and the third generated naturally as the
fourth point machine at Tiruvallur. `validate_demand.py` asserts all three exist, are pending,
span all three departments and stay co-located at Tiruvallur.

Against `compatibility_matrix.csv` they form a valid clique with a **critical path of 180
minutes** against a naive sum of 330 — the Blueprint §6.4 shape.

## A contradiction inside the spec

**§9.1 gives `TRD-2026-01188` as km 40.00–44.00 on `TRL-AJJ-UP`. §8.2 starts that section at
km 42.0.** The sample record describes an OHE inspection running two kilometres before its own
block section begins.

The record is kept **verbatim**, because the spec names these three as the integration test and
silently clamping the range to 42.00–44.00 would make the test pass by editing the test. The
validator reports it as a note with both section references, so it stays visible. It is
realistic in itself — a tower car inspection genuinely runs through a station boundary — and the
resolution is a question for whoever owns the spec: either the section starts earlier than §8.2
says, or the sample record should read 42.00.

## Two cross-table bugs the validator caught

Both were invisible row by row, which is the recurring lesson from this data layer.

**Shared assets.** Eight `SNT-LC-GATE` tasks had no `asset_id`. The generator dropped the asset
whenever its owning department differed from the task's, and level crossings are `ENG` assets.
But a level crossing genuinely has two maintainers — ENG the road surface, S&T the gate
interlocking — and `CMP-028` already models them working it together in one occupation. The rule
is now that a task keeps its asset when its **task type declares it acts on that asset type**,
regardless of who owns it outright.

**Id collision.** A generated `TRD-2026-01188` collided with the §9.1 sample record. Generated
serials now skip the reserved ids.

## Data provenance (spec §12.3)

§12.3 classes individual tasks under **synthesise**, and every row here except the three §9.1
anchors is generated. Nothing is a real TMS, SMMS or TDMS work order.

What is grounded: the schema and every enumeration are the spec's own; task types, access
mechanisms, crew floors and durations come from `task_types.csv`; locations and assets come from
the web-verified geography in `stations.csv` and `block_sections.csv`.

**The standing caveat applies with particular force here.** The origin mix, severity
distribution, safety-critical rate, deadline windows and `materials_ready` rate are all
authored assumptions. A model trained on this corpus recovers those assumptions — it validates
the pipeline, not the railway. On deployment the table is replaced by a live feed from the three
source systems, and only then does any accuracy figure mean anything about Chennai Division.
