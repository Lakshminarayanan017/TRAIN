# train_paths.csv — Train paths (Data Spec §10.1)

The first Supply table (bucket 3, build order §12.5). One row per **(train, block
section)**: the window a train occupies one edge. The window enumerator
(Blueprint §5.2) subtracts these occupations from the day to find the traffic
gaps maintenance can work in, so this file is what makes a "gap" mean something.

Generated by `data/generator/build_train_paths.py`; checked by
`data/checks/validate_supply.py`.

## Schema (Data Spec §10.1)

| Column | Type | Notes |
|---|---|---|
| `path_id` | string | `P-<train_no>-<from><to>-<line_id>`, e.g. `P-12639-TRLAJJ-DN`. Primary key. |
| `train_no` | string | Real IR number for named trains; a representative number in the real series for pattern services. |
| `train_type` | enum | §12.1: `rajdhani_class` / `superfast` / `express` / `passenger` / `EMU` / `MEMU` / `goods` / `special` / `light_engine`. |
| `block_section_id` | ref | The edge occupied — joins to `block_sections.csv`. |
| `entry_time` / `exit_time` | time | `HH:MM`. Computed (see below). |
| `days_of_week` | string | 7 binary digits, Mon→Sun. `1111111` = daily. |
| `priority_class` | int | 1 (highest) … 6 (goods). Weights detention cost in the objective. |
| `divertible` | bool | Can it take a parallel line during a block? `false` on the single-line branch and on dedicated suburban pairs. |

## Real identities, computed timing

This is the design the build was asked for: **real trains, physics for the clock.**

**1. Train identity is real.** The ~26 named long-distance/express services carry
their actual Indian Railways number, type, priority and running days — Mysuru
Shatabdi 12007, Brindavan 12639, Bengaluru Mail 12657/58, Chennai–Bengaluru Double
Decker 22625, Kaveri 16021, Saptagiri 16057, Coromandel 12841, Chennai–Howrah Mail
12839/40, Grand Trunk 12615/16, Tamil Nadu Exp 12621/22, Charminar 12759, the
Egmore Vande Bharat 20627, Vaigai 12635/36, and the return workings. **Chennai-origin
departure times are the real ones where verified** (Shatabdi 06:00, Double Decker
07:25, Brindavan 07:40, Chennai–Howrah Mail 23:45, Coromandel 08:45, Tamil Nadu Exp
22:00, Vaigai 13:40, …).

**2. Per-section times are physics, not a scraped timetable.** For each edge,
`run = length_km / speed × 60`, where `speed = min(train-type cruising speed,
edge sectional_speed_kmph)`. Times accumulate from the origin anchor; stopping
types (EMU/MEMU/passenger) add a short dwell at each block station. So Brindavan
12639 leaves MAS 07:40 and reaches Arakkonam 08:40 — a realistic hour — with every
intermediate edge timed, not copied. This is exactly the "computed times" the brief
chose over exact-timetable scraping.

## What is grounded vs approximate — stated plainly (spec §12.3)

| Element | Status |
|---|---|
| Named train numbers, types, priority, running days | **Real**, verified against public sources. |
| Chennai-origin departure times of named trains | **Real** where quoted above; the rest are reasonable anchors. |
| Return-direction (towards-Chennai) entry times | **Approximate** — the time each enters the pilot at Arakkonam / Gummidipoondi / Tambaram is set to spread traffic realistically, not read off a timetable. |
| Per-section entry/exit clock times | **Computed** from anchor + run-time. Never claimed as timetabled. |
| EMU / MEMU / goods high-frequency services | **Frequency is grounded** (Blueprint §5.3, §12.3 "approximate suburban headways"); individual service numbers are representative, drawn in the real IR series (43xxx/41xxx/66xxx/44xxx/55xxx), not specific timetabled trains. |

Sources: Wikipedia (Brindavan Express, Bengaluru–Chennai Shatabdi, Howrah–Chennai
Mail, Coromandel Express), and train-listing sites (erail / ixigo / IndiaRailInfo)
for numbers, types and departure times. Per the spec §7.1 caveat these are
illustrative for the pilot; the relative model comparison is the claim.

## Volume and the daily_train_count reconciliation

**6,378 rows over 1,118 daily services.** The spec's §12.4 figure of ~15,000 is an
estimate for a full year of pathing; this is one representative operating day
(both directions), which is what the window enumerator consumes. Frequency is
tunable through the headways in `PATTERNS` — halving them roughly doubles the file.

`validate_supply.py` compares each edge's generated path count against
`block_sections.daily_train_count` (the reference layer's independent anchor). The
two match well on the suburban pairs — the busy Beach–Egmore slow line lands near
its 200/day, and the trunk suburban reproduces the real thinning outward from
Chennai (frequent EMU turns back at Avadi, only the MEMU carries on to Arakkonam).

The **eight remaining notes are trunk main-line undercounts** (≈20 paths against an
80–95 anchor), and they are deliberate. The trunk main carries dozens of expresses
to Bengaluru, Tirupati, Katpadi, Salem and Kerala every day; this file enumerates
only the ones whose number and type it can state truthfully, plus goods. Padding
the main line up to the anchor would mean inventing ~60 train numbers and times —
exactly the fabrication the brief rules out. The honest undercount is preferred,
and it is surfaced by the validator rather than hidden.

## Direction and line convention

A service away from Chennai (increasing chainage) runs on the DN / DN_SUB group; a
service towards Chennai runs on UP / UP_SUB; the branch runs SINGLE either way.
This matches `block_sections.csv`, where `from_station` is the lower-chainage end
and `line_id` is the only thing separating parallel edges. The validator fails any
train number that appears on both an UP and a DN line — a single physical train
runs one way.
